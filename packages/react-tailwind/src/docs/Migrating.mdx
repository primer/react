# Migrating from Primer React

This package keeps Primer's component names and, wherever it can, their props. Most of a migration is mechanical. What follows is what actually changes; each component's **Alignment** page records its own differences.

## Styling

`sx` and styled-system props are gone. Use `className` with Primer's semantic utilities, and a token when no utility exists.

```tsx
// Before
<Button sx={{mt: 2, width: '100%'}}>Save</Button>
<Box sx={{p: 3, bg: 'canvas.subtle'}} />

// After
<Button className="mt-2 w-full">Save</Button>
<div className="rounded-md bg-muted p-4" />
```

There is no `Box`. Use a plain element with `className`, or `Stack` when you want gap and direction props.

Because Tailwind silently ignores an unknown class, the package runs a build check that fails on any class generating no CSS. Watch for utilities that do not exist here, most commonly Tailwind's default type scale: `text-base` and `text-lg` are replaced by `text-body-medium`, `text-body-large`, and the title sizes.

## Composition

Interactive components are built on Base UI, so use `render` to project behavior onto another element rather than `as`.

```tsx
// Before
<Button as="a" href="/settings">Settings</Button>

// After
<LinkButton href="/settings">Settings</LinkButton>
<Button render={<a href="/settings" />}>Settings</Button>
```

Presentational components still take `as`, for example `<Stack as="section">`, `<Text as="span">`, and `<Card as="article">`.

Compound parts follow Base UI naming: `Root`, `Trigger`, `Portal`, `Positioner`, `Popup` or `Content`, `Title`, `Description`, and `Close`. Parts may be grouped in fragments anywhere in the package.

## Names that changed

Experimental and versioned components are promoted to their stable names. Use `Dialog`, not `DialogV2`. Use `Tooltip`, not `TooltipV2`. Use `SelectPanel`, not `SelectPanel2`. Use `Breadcrumbs`, not `Breadcrumb`.

Deprecated APIs are not included:

| Removed                      | Use instead                                                    |
| ---------------------------- | -------------------------------------------------------------- |
| `CircleBadge`                | An Octicon from `@primer/octicons-react` with your own styling |
| `SideNav`                    | `NavList`                                                      |
| `TextInputWithTokens`        | `TextInput` composed with `Token`                              |
| `Breadcrumb`                 | `Breadcrumbs`                                                  |
| `SelectPanel2`               | `SelectPanel`                                                  |
| `useRefObjectAsForwardedRef` | Pass `ref` as a prop; React 19 needs no hook                   |
| `useResponsiveValue`         | Responsive class names or CSS media queries                    |

## Values that changed

Sizes read `small`, `medium`, and `large` everywhere. Two components inherited a different middle value upstream and were normalized:

| Component        | Before                              | After                                |
| ---------------- | ----------------------------------- | ------------------------------------ |
| `KeybindingHint` | `size="normal"`, `variant="normal"` | `size="medium"`, `variant="default"` |
| `ProgressBar`    | `barSize="default"`                 | `size="medium"`                      |

`ProgressBar` also renames `barSize` to `size` and `bg` to `variant`.

## Contracts deliberately kept

A few APIs stay as they are upstream so existing handlers port unchanged, even though they differ from the package's usual conventions:

- `Pagination`'s `onPageChange(event, page)` keeps its event-first argument order.
- `SelectPanel`'s `onOpenChange(open, gesture)` reports a gesture rather than Base UI change details.
- `SelectPanel.disableFullscreenOnNarrow` is opt-out while `FilteredActionList.fullScreenOnNarrow` is opt-in.

## Internals that are no longer exported

Upstream implementation utilities are not part of this package's contract, including `useSlots`, `isSlot`, `asSlot`, `useFocusZone`, `useAnchoredPosition`, `useOnOutsideClick`, `useMergedRefs`, and `createComponent`. Base UI provides the equivalent behavior inside the components that need it.

`RelativeTime` no longer depends on a custom element; it renders a semantic `time` element, so tests can read its text directly.

## Replacing the slot system

`useSlots` is the removed utility most likely to affect you: it appears in roughly 28 places across `github/github-ui`. Those apps do not use it to consume Primer — they use it to build their **own** compound components on top of Primer.

Separately, and more disruptively, `__SLOT__` is assigned directly in 13 places there. `asSlot` and `isSlot` are unused, but the marker itself is load-bearing. `CollapsibleSidebar` sets `__SLOT__: PageLayout.Sidebar.__SLOT__` so a completely custom component can be dropped into `PageLayout` as its sidebar; `BulkSelectorGroup` adopts `ActionList.Group.__SLOT__`; `ExpirationSelect` and `OrganizationSelect` adopt `Select.__SLOT__`. There are tests asserting this behaviour.

**This package cannot support that today.** Its parts match children by identity, and where a marker does exist — `PageLayout` — the symbol is internal and not exported, so a consumer cannot opt into a slot. Anything relying on adopting or forwarding `__SLOT__` needs the owning component to grow a supported extension point before it can migrate. Treat that as a blocking dependency rather than something to work around in application code.

The rest of this section covers the patterns that do carry over.

### Extract named children yourself

The replacement is a small local helper rather than a package import. It has no dependency on Primer internals, so it will not break again when a design system changes:

```tsx
function flattenChildren(children: React.ReactNode): React.ReactNode[] {
  return React.Children.toArray(children).flatMap(child =>
    React.isValidElement<{children?: React.ReactNode}>(child) && child.type === React.Fragment
      ? flattenChildren(child.props.children)
      : child,
  )
}

function useParts<T extends Record<string, React.ElementType>>(children: React.ReactNode, config: T) {
  const all = flattenChildren(children)
  const parts = {} as {[K in keyof T]?: React.ReactNode}
  const rest: React.ReactNode[] = []

  for (const child of all) {
    const key = React.isValidElement(child)
      ? (Object.keys(config) as Array<keyof T>).find(name => child.type === config[name])
      : undefined
    if (key && parts[key] === undefined) parts[key] = child
    else rest.push(child)
  }

  return [parts, rest] as const
}
```

```tsx
// After
const [{header, headerActions, blankslate, rows}, children] = useParts(slottedChildren, {
  header: PanelList.Header,
  headerActions: PanelList.HeaderActions,
  blankslate: PanelList.Blankslate,
  rows: PanelList.Rows,
})
```

The call site is unchanged, and the `?? default` fallback and trailing `children` behave as before. It keeps `useSlots`'s ordering semantics too: the first element matching a key wins, later duplicates fall through to `rest`, and `rest` stays in author order. Flattening fragments matches how this package's own compound components read their children, so authors can group parts in a fragment without breaking matching.

### Prefer props for single values

If a slot only ever carries a value rather than markup, a prop is simpler than extraction and gives you types for free:

```tsx
<PanelList header={<Header title="Alerts" />} />
```

Reserve child extraction for cases where the parent genuinely needs to place authored markup in several positions.

### Wrapping a part so the parent still recognizes it

This is the one capability that does not carry over, and there is no workaround against this package's components. `asSlot` copied a `__SLOT__` marker onto a wrapper so the parent kept matching it. These components match children by component identity, so a wrapper around one of their parts is no longer matched as that part:

```tsx
// Card matches on identity, so this is not treated as the heading
const CardHeadingWithTooltip = props => <Card.Heading {...props} />
```

The wrapped content still renders, but the parent places it with ordinary children rather than in the slot's position, so layout and any behavior keyed to that slot change. For `Card` specifically, a `section` card derives its `aria-labelledby` from the heading it matched, so a wrapped heading also loses that association.

`PageLayout` matches its parts with an internal `Symbol` marker rather than identity, but that symbol is not exported, so its parts are no more wrappable than any other. Every part in this package is effectively wrap-intolerant.

So, in order of preference:

- Use `render` on Base UI-backed parts to project them onto your own element instead of wrapping them. Components that pass Base UI's props through accept it, including `Button`, `LinkButton`, and the `Trigger` parts of `Dialog`, `Popover`, and `Tooltip`. Check the part's props if you are unsure.
- Use `as` on presentational parts such as `Card.Heading` and `Text` to change the element without wrapping.
- Render the part directly and move your customization inside it.
- Lift the wrapper up so it renders around the whole compound component instead of around one of its parts.

### Wrapper tolerance in your own components

Base UI's model is the place to start, but it has an SSR constraint that decides which form you want.

Slots exist because a parent has to _find_ a child in order to position it or read something off it. Base UI inverts that: the child publishes what the parent needs through context. Its own `Dialog` works this way, with `Dialog.Title` publishing its id and `Dialog.Popup` reading it for `aria-labelledby`, and no child scanning anywhere.

The catch is that publishing upward happens in an effect, and effects do not run on the server. A parent that reads a value registered by a child renders **without** it in server HTML, and only picks it up after hydration. That is fine for overlays, which are client-only regardless — Base UI's `Dialog` renders nothing at all on the server — but it is wrong for content that must be correct in the server response.

#### Allocate the id downward, not upward

When the coordination is server-rendered, have the parent allocate during render and pass the value down. The child claims it instead of announcing it:

```tsx
import {useRender} from '@base-ui/react/use-render'

const PanelContext = React.createContext<{headingId?: string}>({})

function Panel({children}: {children?: React.ReactNode}) {
  const headingId = React.useId()
  const value = React.useMemo(() => ({headingId}), [headingId])
  return (
    <PanelContext.Provider value={value}>
      <section aria-labelledby={headingId}>{children}</section>
    </PanelContext.Provider>
  )
}

function PanelHeading({render, ...props}: {render?: useRender.RenderProp} & React.ComponentPropsWithRef<'h2'>) {
  const {headingId} = React.useContext(PanelContext)
  return useRender({defaultTagName: 'h2', render, props: {...props, id: props.id ?? headingId}})
}
```

This renders `<section aria-labelledby="…"><h2 id="…">` on the server, and it still resolves when a consumer wraps the heading, nests it arbitrarily deep, or projects it onto another element with `render`. None of those survive a `child.type === Part` check or a `__SLOT__` marker, so you keep the wrapper tolerance without giving up SSR.

Its limitation is that the parent cannot tell whether the child is actually present, so only label unconditionally when the part is required. Otherwise let the consumer opt in.

#### When to use which

- **Server-rendered, and the parent must know a child exists.** Read children during render. Identity matching is correct here, and it is what `Card` does to decide whether to set `aria-labelledby` at all. This is the one case the old slot system served that context cannot.
- **Server-rendered, and the child is required.** Allocate downward, as above. SSR-safe and wrapper-tolerant.
- **Client-only and interactive**, such as overlays and menus. Effect-based upward registration is fine and is what Base UI does.

`useRender` gives your part the same `render` contract Base UI parts have, so consumers compose instead of wrapping; `LinkButton` in this package is a worked example. Use `mergeProps` from `@base-ui/react/merge-props` to combine your props with a consumer's by hand.

If you must both scan children and tolerate wrappers, a `Symbol` marker is the fallback. It has to be copied onto each wrapper deliberately, since that is the job `asSlot` used to do:

```tsx
const SECTION = Symbol('MyLayout.Section')
const withSectionMarker = <T,>(component: T): T => Object.assign(component as object, {[SECTION]: true}) as T
```

### Moving children into a different position

This is the case context cannot serve. `PanelList` in `github-ui` writes `Header`, `Rows`, and `Blankslate` as flat children and then renders the header above a box and the rows inside it. The parent is not reading a value off the child, it is relocating it, so it has to see the children.

Read them during render. That is SSR-safe, unlike a portal, which renders nothing on the server — `renderToString` of a `Portal` produces an empty parent — so portals are not a way to reposition server-rendered content.

```tsx
const parts = flattenChildren(children)
const header = parts.find(isHeader)
const rest = parts.filter(child => child !== header)

return (
  <div>
    {header}
    <div className="body">{rest}</div>
  </div>
)
```

Match with identity when your parts are never wrapped, and with a `Symbol` marker when they are. `PageLayout` in this package uses markers for exactly that reason: `SplitPageLayout` wraps its `Header`, `Sidebar`, and `Footer`, and marker matching is what keeps those wrappers recognizable.

Two things to know before relocating a child:

- A relocated child reads context from where it is **rendered**, not where it was written. Moving it inside a provider changes what it sees, which is easy to miss when the move is only meant to be positional.
- Relocation changes DOM order, and with it reading order and tab order.

Because of that second point, prefer these when they fit:

- **A prop**, when the part is a single value rather than free-form markup. `<Panel header={<Header />} />` is typed, SSR-safe, and wrapper-tolerant by construction, because the consumer hands you the element instead of you finding it.
- **CSS**, when the move is only visual. Grid areas and `order` reposition a child without touching the tree, so the DOM keeps its authored reading and tab order. Reach for tree manipulation only when the child needs a different parent element, not merely a different position on screen.

## Suggested order

1. Set up `ThemeProvider`, `BaseStyles`, and the stylesheet, as described in **Get started**.
2. Replace `sx` and `Box` first; that accounts for most of the diff.
3. Swap deprecated components for their replacements.
4. Run your build and check for classes that generate no CSS.
5. Review the **Alignment** page of any component whose behavior looks different.
