This rubric evaluates a component against the accepted benchmark target. It records current-contract defects and unweighted candidate checks separately and never changes production APIs, ADR status, release status, or merge policy. Scores from 0.4.1, 0.5.0, and 0.6.0 are not comparable.

## Purpose and authority

Establish the component's own stated contract from exports, types, docs, and tests before grading. Report a reachable violation of that contract as a `DEFECT`. Then grade compliance with active accepted-target requirements; missing active requirements are `ADR GAP`s even when the released component never promised them. Candidate requirements are reported separately until they are promoted into a versioned active rubric. The active accepted-target score is the headline result. Keep current-contract defects and candidate findings outside the active grade.

An accepted-target gap is a `FIX` or `NIT`. A `BLOCK` is reserved for a reachable current-contract defect or an objective accessibility/native-platform violation. Any open `BLOCK` caps the overall letter grade at D. Record the BLOCK count separately from target-gap counts.

## Target baseline

Use the [pinned target baseline](./target-baseline.md) for ADR scope, composition requirements, precedence, mappings, and open decisions. It defines the benchmark for the audited snapshot without changing ADR status or asserting that a proposal has shipped. Apply shape-based exclusions from Applicability; do not infer N/A from a missing target feature.

Rubric 0.6.0 scores one active set totaling 92 points. `PART-RENDER` is an unweighted candidate with proposed weight 8; it does not affect the score, denominator, caps, or status. Grade the five merge checks from current public behavior. Promote candidates only through a versioned rubric change and a full rerun.

## Grading modes

| Mode            | Scope                                                                                                          | Output                                                                         |
| :-------------- | :------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------- |
| Whole component | One named component at a pinned commit; complete the stated-contract review and every applicable active target check. | One active target score, candidate checks, current-contract context, evidence matrix, and ledger input. |
| PR review       | Grade only API behavior introduced or changed by the diff; compare base and head.                              | Delta findings with no whole-component grade or ledger entry.                  |
| Nightly         | Future automation may run one isolated whole-component grader per component and aggregate its output.          | Future work only; no automation or merge gate is created by this rubric.       |

## Audit procedure

1. Record component name, import/export paths, docs maturity metadata, repository package version, audited SHA, and mode. Keep published-package metadata separate; verify a published surface only when a recommendation changes an existing released API. Root export and sample selection do not prove stable status.
2. Read the component's own public contract from exports, types, docs, stories, implementation, and focused tests. Record contract defects separately from target gaps.
3. Classify component shapes and complete one verdict row for every active check ID and candidate check ID. Apply every interactive-part requirement to interactive leaves. Record `N/A` only with a shape-based reason.
4. Record focused unit/integration test execution as `TEST-01` evidence. Separately inspect the snapshot policy (`SNAPSHOT-01`) and Storybook Playwright interaction policy (`INTERACTION-01`); run the smallest relevant Playwright test when feasible. Keep source structure, execution, agent judgment, and human verification as separate evidence classes.
5. Link each active gap to one owning finding and one owning check. Record candidate gaps under `candidateFindings`; they do not enter the active score or active finding count. Use `COVERED` only when a second active check is independently unmet by the same underlying behavior and shares the owning fix. Never use `COVERED` for a merge check solely because `PART-RENDER` is absent; inspect current root and part behavior.
6. Fill the Layer 3 review form with `PENDING HUMAN` until a human reviewer supplies each required judgment. An agent's opinion is `AGENT JUDGMENT`, not human sign-off.
7. Run the deterministic validator on the structured scorecard data. Confirm all section scores, the threshold grade, caps, distinct finding counts, and BLOCK sensitivity match the rendered report.
8. Verify every cited `path:line` against the pinned source SHA. Record the exact test, type-check, and validator commands and their outcomes.

A single interactive leaf may use its public root as its parts surface; this does not waive `PART-AS` or the part merge checks. `PART-RENDER` is currently a candidate check outside the active score.

## Candidate checks

Candidate checks are visible assessments outside the active rubric. They have no active weight and do not affect the official grade, applicable-weight denominator, section caps, evidence coverage, or status. Record each candidate with a verdict, evidence, and a reason when it is N/A, NOT MEASURED, or UNRESOLVED. Candidate GAPs link to a separate candidate finding with a reachable use case, additive fix, and pinned citations. Report proposed weights separately from active weights.

| ID             | Section | Proposed weight | Verification class | Severity | Candidate criterion / source                                                                                                                              |
| :------------- | :-----: | :-------------: | :----------------: | :------: | :-------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PART-RENDER`  |    2    |        8        |        semi        |   FIX    | Every interactive part supports render-element and render-function forms; the function receives required props and current state. Preserve existing renderer signatures. Pinned composition gist. |

Promote a candidate only after a rubric decision. Assign it an active weight, adjust section weights, bump the rubric version, update the structured audit schema, and rerun every affected component. Do not publish a second grade with selected checks removed. Candidate `NOT MEASURED` and `UNRESOLVED` states are visible, but do not make the active grade provisional.

## Evidence and verdicts

Every scorecard contains exactly one row for every active check ID and a separate row for every candidate check ID. Use these verdicts:

| Verdict        | Meaning                                                                                                                                                                                                                                                        | Scoring treatment                                                                                                                                                             |
| :------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PASS`         | The property is verified with the evidence required by its check.                                                                                                                                                                                              | Earn the full check weight.                                                                                                                                                   |
| `GAP`          | The accepted target or current contract is violated and has one owning finding ID.                                                                                                                                                                             | Earn zero check weight.                                                                                                                                                       |
| `N/A`          | The shape or contract makes the requirement inapplicable; provide a specific reason.                                                                                                                                                                           | Exclude the check weight from the section denominator.                                                                                                                        |
| `COVERED`      | A related target check is unmet for the same underlying issue as its owning finding; include that finding ID.                                                                                                                                                  | Keep the weight in the denominator and award zero; do not create another distinct finding or section cap.                                                                     |
| `NOT MEASURED` | Required evidence was not run or cannot be obtained. Include the missing command/source and reason.                                                                                                                                                            | Keep the check weight in the denominator as unknown; do not score it as a pass or zero. Report a provisional score range.                                                     |
| `UNRESOLVED`   | The target explicitly leaves a decision open or the reviewer cannot resolve it from evidence. State the decision and scope.                                                                                                                                    | Keep the check weight in the denominator as unknown; do not score it as a pass or zero. Report a provisional score range.                                                     |

Every row records an evidence class: `SOURCE VERIFIED`, `EXECUTION VERIFIED`, `BEHAVIOR VERIFIED`, `AGENT JUDGMENT`, or `PENDING HUMAN`. Source inspection proves structure only. `TYPE-01`, `TEST-01`, and `INTERACTION-01` cannot pass without `EXECUTION VERIFIED`; runtime claims need an executed test or observable behavior result. A `PENDING HUMAN` evidence row must remain `UNRESOLVED`, and an audit must explicitly carry a boolean `pendingHuman` value. Human review rows remain pending until an actual human supplies the judgment. An agent-filled review form never counts as human sign-off.

`COVERED` rows are measured failures and remain in the active denominator with zero earned weight. Grouping related checks under one finding prevents duplicate issue counts while preserving every unmet active target obligation in the grade. Never attach merge checks to a candidate finding solely because render support is absent. Active `NOT MEASURED` and `UNRESOLVED` rows remain in the active denominator as unknown evidence, not zero-valued failures or passes. Candidate verdicts and findings are reported separately and never enter the score, active evidence coverage, caps, or provisional-status calculation. A section is `LIMITED` when less than 50% of its active section weight is applicable, regardless of verdict. Still score every applicable active row, apply the distinct-finding cap, and include its applicable weight in the overall denominator; `LIMITED` never hides a failure or removes weight when a GAP is fixed. For every section, compute the lower bound as `5 × earned PASS weight / applicable weight` and the upper bound as `5 × (earned PASS weight + unknown weight) / applicable weight`, then apply the same mechanical cap to both bounds. Report an exact score only when the bounds are equal. Aggregate section bounds by their applicable active weight. Keep the result provisional when an active section is limited or active evidence/human judgment is incomplete.

## Findings and citations

Each finding has a unique ID, classification (`DEFECT` or `ADR GAP`), severity, one owning section/check, affected check IDs, reachable consumer path, observed behavior, concrete additive fix, and evidence. A finding cites its check ID and one or more exact `path:line` references with the full audited commit SHA. Every `GAP` row points to exactly one finding. Every finding has exactly one primary `GAP` row. Related unmet rows use `COVERED` and the same finding ID; each covered row's check weight still scores zero in the denominator.

A reachable victim is a valid consumer invocation or documented user state that reaches the behavior. A type-rejected, undocumented input is not a reachable victim. Group observations with one owning fix into one distinct finding; report raw observations separately. A finding appears in only one owning section. New-part policy gaps are FIX-level `ADR GAP`s; existing contract and objective violations may be BLOCK-level `DEFECT`s.

For each recommendation that changes a released surface, retain existing props, callback signatures, and behavior through an additive path or a documented versioned migration. Apply `MIG-01` only when the recommendation depends on an API confirmed in a published package. Mark it `N/A` when the proposed changes only add new surfaces; record repository package version separately. A registry lookup that cannot establish publication is not evidence that an API is absent.

## Scoring and validation

Active check weights in each section sum to that section's active weight; active section weights total 92. The 8-point `PART-RENDER` proposal is unweighted and kept in the candidate register. The calculator normalizes applicable active weight to a 100-point grade. For each section, `applicable weight` is the sum of active check weights except `N/A`, including `COVERED`. Earned weight is the sum for `PASS` rows only. `NOT MEASURED` and `UNRESOLVED` weights are unknown and contribute to the score interval, never as a fixed zero. `COVERED` weights are measured failures and score zero. Compute lower and upper section scores using the interval formula above and report two decimal places. Apply the mechanical cap to both bounds. Every section with applicable active rows contributes its applicable weight to the overall denominator, including limited sections. Count scored raw observations as active `GAP` and `COVERED` rows plus current-contract findings; count candidate gaps separately. Count scored distinct findings by unique active finding ID after grouping related observations under one owner.

| Open distinct findings owned by section | Maximum section score |
| :-------------------------------------- | :-------------------: |
| 1 BLOCK                                 |           3           |
| 2 BLOCKs                                |          2.5          |
| 3 BLOCKs                                |           2           |
| 4 or more BLOCKs                        |           1           |
| No BLOCK and 1–2 FIX/NIT findings       |           4           |
| No BLOCK and 3–4 FIX/NIT findings       |           3           |
| No BLOCK and 5 or more FIX/NIT findings |           2           |

Compute each endpoint of the overall target score range as `100 × sum(applicable check weight × capped section endpoint / 5) / sum(applicable check weight)`. A limited section contributes its applicable check weight and score. Report a single numeric score and grade only when the range endpoints match; otherwise report the score interval and corresponding letter-grade interval. Grade endpoints use A (90–100), B (80–89.99), C (70–79.99), D (60–69.99), and F (below 60). An open BLOCK caps each letter-grade endpoint at D. The 78.5 boundary is C; 80.0 is B.

Report `CONCLUSIVE`, `PROVISIONAL`, or `UNKNOWN`. Any `NOT MEASURED`, `UNRESOLVED`, limited section, or pending human review makes the result `PROVISIONAL`; show the calculated provisional score range, check-evidence coverage, and grade range. Use `UNKNOWN` when no scored section exists. Only use `CONCLUSIVE` when all applicable checks and required evidence are complete and required human judgments have been supplied.

The scorecard reports `BLOCK count`, `distinct defects`, and `raw findings` separately. Its sensitivity line is “Fix the N open BLOCKs, change nothing else → projected X / grade Y.” Recalculate with each BLOCK finding's primary check changed to PASS and the BLOCK cap removed; preserve every other verdict and evidence state.

Run `.agents/skills/component-api-design/references/scorecard-calculator.mjs` against the structured JSON audit data. The calculator emits one active grade and a separate candidate assessment. It validates active and candidate check coverage, verdicts, evidence classes, N/A reasons, finding ownership/counts, section caps, grade thresholds, provisional status, and sensitivity. Focused tests run with `node --test .agents/skills/component-api-design/references/scorecard-calculator.test.mjs`.

## Layer 3 human review

Complete the Layer 3 form in the scorecard template after source and runtime checks. Record rationale, a reachable use case, and the reviewer. Keep each item `PENDING HUMAN` until a human supplies the judgment; agent judgment is not sign-off.

## Recording results

Return whole-component scorecards and their structured JSON to the caller. To publish a completed grade, manually dispatch the `Component API grade report` workflow with that audit JSON and its rendered scorecard Markdown. For multiline input, prepare an untracked JSON file with `audit_json` and `scorecard_markdown` string fields and run `gh workflow run component-api-grade-report.yml --json < report-input.json`. The workflow revalidates the audit, confirms the scorecard component and source SHA, and uploads the scorecard, audit JSON, and calculated summary as a 90-day artifact. Generated grade files are never committed.

The workflow maintains one program parent issue, one component child issue per graded component, and one finding child issue per check with a `GAP`, `COVERED`, candidate `GAP`, or open current-contract defect. Stable markers let retries update the same issues. Finding issues close only when their check is explicitly `PASS` and no open contract defect remains for that check. `N/A`, `NOT MEASURED`, `UNRESOLVED`, absent checks, invalid audits, and failed grading do not close issues. A partially failed API sync can be rerun safely; the uploaded artifact remains available.

PR reviews grade the changed diff only and return delta findings. Automatic grade generation, scheduled component fan-out, and dispatching reports directly from grader-agent output remain future work.
